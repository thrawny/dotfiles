# `concurrently` alternatives for these dotfiles

_Research date: 2026-08-09. Sources are first-party project documentation, repositories, release pages, and Nixpkgs definitions._

## Recommendation

Do **not** install `concurrently` globally. Keep **`just` as the default for finite repository workflows**, including parallel checks, and put `concurrently` in a project's `devDependencies` when a `package.json` genuinely needs its behavior. This repository already installs `just`, Node 24, and pnpm 11 through Home Manager's [shared core package list](../nix/home/shared/packages/core.nix), and its root [Justfile](../Justfile) already uses a `[parallel]` dependency group for `check-parallel`. Adding another global runner would mostly duplicate an established, language-neutral convention.

This is also the more reproducible split:

- Repository commands and globally useful tools stay in the Nix-pinned Home Manager environment. The repository convention puts shared global packages in [`nix/home/shared/packages/*.nix`](../nix/AGENTS.md), so a global CLI would be added as `concurrently` (not installed imperatively with npm) to `core.nix`, then activated with `just switch`. Nixpkgs has a first-class [`concurrently` derivation](https://github.com/NixOS/nixpkgs/blob/70ce234312134a463ba7728e94da2486a1d237ac/pkgs/by-name/co/concurrently/package.nix), but its packaged version can lag upstream; at the research date upstream was [10.0.4](https://github.com/open-cli-tools/concurrently/releases/tag/v10.0.4).
- A Node project's runner belongs in that project's lockfile. Upstream itself [recommends a local development dependency](https://github.com/open-cli-tools/concurrently#installation). That keeps the script portable to contributors and CI without assuming these personal dotfiles.
- For a one-off outside a project, use the repository's existing ephemeral-tool convention, for example `, concurrently ...` or `nix shell nixpkgs#concurrently -c concurrently ...`, rather than enlarging every host's Home Manager closure.

For **interactive, cross-project process management**, `just` and `concurrently` are the wrong abstraction. This repository already exposes [`zmx`](https://github.com/thrawny/zmx) for persistent named sessions with attach/detach, history, send, kill, and wait. If a single dashboard should own several related services, **Process Compose is the strongest optional global addition**: it is a dependency-free Go binary with a TUI, process groups, health/dependency modeling, restart policies, and explicit shutdown behavior. Add it only after a recurring workflow demonstrates that need.

A read-only evaluation of the repository's [locked Nixpkgs input](../nix/flake.lock) found `concurrently` 9.2.1, `mprocs` 0.9.6, Process Compose 1.120.0, Overmind 2.5.1, `just` 1.57.0, and pnpm 11.18.0 on its x86-64/aarch64 Linux and aarch64 macOS targets; `npm-run-all2` had no package attribute. Thus every viable global candidate except `npm-run-all2` has a straightforward, pinned `home.packages` route, but the locked `concurrently` is behind upstream.

## Two different jobs

1. **One project's scripts:** build, lint, tests, or several dev watchers described by one `package.json`. Prefer project-local pnpm, `npm-run-all2`, or `concurrently` depending on required semantics.
2. **Interactive or cross-project services:** API in one checkout, frontend in another, database, workers, and processes that need individual restart/input/log views. Prefer Process Compose, `mprocs`, Overmind, or the already-installed `zmx`; do not encode this as a long quoted `concurrently` command in global shell state.

## Comparison

| Tool | Best fit | Cleanup, failure semantics, and output | Config, portability, and footprint | Maintenance and reproducibility |
|---|---|---|---|---|
| **`just` + shell (default)** | Finite repo tasks and a discoverable task API. `[parallel]` runs recipe dependencies concurrently, exactly as this repo already does; the [official manual](https://just.systems/man/en/parallelism.html) documents the attribute. | Normal recipe exit codes make it appropriate for gates. `just` waits for a running child on fatal signals and forwards `SIGTERM` sent directly to it, avoiding an immediate orphan; see its [fatal-signal contract](https://github.com/casey/just#fatal-signals). It has ordinary interleaved terminal output, not named/prefixed streams or a service TUI. A raw shell `cmd1 & cmd2 & wait` needs explicit PID tracking and `trap` cleanup, and nuanced aggregate failure logic; Bash's [`wait`](https://www.gnu.org/software/bash/manual/html_node/Job-Control-Builtins.html) and [signal](https://www.gnu.org/software/bash/manual/html_node/Signals.html) rules are primitives, not a supervisor. | Near-zero additional config and footprint here because `just` and Bash are already installed. `just` runs on Unix and Windows with a suitable/configured shell, but arbitrary shell recipes are only as portable as their commands. | Active and packaged as a checked Rust build in [Nixpkgs](https://github.com/NixOS/nixpkgs/blob/70ce234312134a463ba7728e94da2486a1d237ac/pkgs/by-name/ju/just/package.nix). The Justfile and Nix lock are reviewable and pinned. Best match for this repo; not an interactive process manager. |
| **`concurrently`** | Arbitrary commands or npm scripts in one project, especially when Windows contributors need identical invocation. | Prefixed/colorized merged logs, optional stdin routing, restart attempts, maximum concurrency, configurable kill-on-success/failure, and `all`/`first`/`last` success conditions are part of its [documented CLI/API](https://github.com/open-cli-tools/concurrently#concurrentlycommands-options). `--kill-others` improves cleanup when one command exits; its `Command.kill()` accepts a signal. It is still a foreground log multiplexer rather than a per-process dashboard. | Very low config for two commands, but quoting grows brittle as commands/env/cwds multiply. Cross-platform. Requires Node >=22 in current v10 and brings several runtime packages including RxJS, yargs, and `tree-kill`; see the upstream [package manifest](https://github.com/open-cli-tools/concurrently/blob/main/package.json). | Actively released ([10.0.4](https://github.com/open-cli-tools/concurrently/releases/tag/v10.0.4)); Nixpkgs packages it declaratively. Prefer a project-local locked dependency, because a Home Manager version is unrelated to each project's lockfile and can lag the npm release. |
| **`mprocs` (now `dekit`)** | Interactive development: switch among separate process outputs, send input, restart one process, or run a full-screen program inside the selected pane. | On quit it soft-stops processes and waits; force quit is available. Per-process `stop` can be `SIGINT`, `SIGTERM`, `SIGKILL`, hard kill, keystrokes, or a cleanup command; `autorestart` is optional. The TUI shows each process separately rather than interleaving logs. These are [documented controls](https://github.com/pvolok/dekit/blob/master/README-mprocs.md#config). It shows per-process failure state, but is not primarily a deterministic CI exit-code aggregator. | One Rust executable; accepts CLI commands, `mprocs.yaml`, `package.json --npm`, or a Procfile. Upstream distributes Linux, macOS, and Windows builds, while the [Nixpkgs `mprocs` package](https://github.com/NixOS/nixpkgs/blob/70ce234312134a463ba7728e94da2486a1d237ac/pkgs/by-name/mp/mprocs/package.nix) is marked Unix. More UI value than `concurrently` for roughly the same simple config. | Active: stable 0.9.6 plus rolling builds in the [release stream](https://github.com/pvolok/dekit/releases). The project/repository has been renamed to **dekit**, although Nixpkgs and the legacy executable remain `mprocs`; that transition is a small naming/churn cost. Good interactive runner, but it overlaps `zmx` and is not needed for current dotfiles tasks. |
| **Process Compose** | A real local service stack: dependencies, readiness/liveness checks, ordered startup/shutdown, restarts, replicas, namespaces, detached control, and interactive management. | Default shutdown sends `SIGTERM` to the **process group**; configurable signal/command/keystrokes and timeout escalate to `SIGKILL`. `exit_on_failure` shuts down peers and returns the failed process's code; `exit_on_end` supports test-with-dependencies workflows; successful signal exit codes can be allowlisted. These semantics are explicit in [Processes Lifetime](https://f1bonacc1.github.io/process-compose/launcher/). The default TUI provides individual status, logs, start/stop/restart, signals, and a dependency graph ([TUI docs](https://f1bonacc1.github.io/process-compose/tui/)). | Highest YAML burden, rewarded by the strongest lifecycle model. A single Go binary with no other runtime dependencies, per the [official README](https://github.com/F1bonacc1/process-compose#process-compose); binaries exist by OS and Nix is officially documented in its [installation guide](https://f1bonacc1.github.io/process-compose/installation/). | Very active: [1.120.0 was released 2026-07-11](https://github.com/F1bonacc1/process-compose/releases/tag/v1.120.0), and Nixpkgs has a pinned [`process-compose` derivation](https://github.com/NixOS/nixpkgs/blob/70ce234312134a463ba7728e94da2486a1d237ac/pkgs/by-name/pr/process-compose/package.nix). Best optional global supervisor if `zmx` plus project recipes cease to be enough. |
| **Overmind** | Procfile-based app stacks where attaching to a process's real tmux pane and preserving native TTY/color behavior matters. | A process death normally interrupts the rest; `--can-die` exempts selected processes, and per-process auto-restart is available. It can connect, stop, restart, kill, daemonize, and later attach; tmux control mode preserves unmodified output. The [README documents these semantics](https://github.com/DarthSim/overmind#overmind-features) and also notes Docker cleanup needs an explicit trap. | Very small Procfile, but adds tmux, sockets, and Overmind-specific env configuration. Linux/BSD/macOS only, no Windows. The [Nixpkgs wrapper](https://github.com/NixOS/nixpkgs/blob/70ce234312134a463ba7728e94da2486a1d237ac/pkgs/by-name/ov/overmind/package.nix) explicitly puts `tmux` and `which` on its runtime `PATH`, so it is materially heavier and overlaps this repo's tmux/zmx setup. | Stable but slower-moving: latest 2.5.1 is from [2024-03-26](https://github.com/DarthSim/overmind/releases/tag/v2.5.1). Reproducible in Nixpkgs, but not the default unless Procfile/tmux compatibility is the requirement. |
| **`npm-run-all2`** | Several named scripts in one `package.json`, especially glob groups such as `watch:**`, or mixed sequential/parallel stages. | `run-p` fails fast: a non-zero task kills other tasks and descendants with `SIGTERM` (Windows: `taskkill.exe /F /T`). `--continue-on-error` finishes all but still returns non-zero; `--race` kills peers after the first success. It offers optional labels or aggregate output, with a documented TTY/color caveat. See the [`run-p` reference](https://github.com/bcomnes/npm-run-all2/blob/master/docs/run-p.md). | Cross-platform Node package with essentially no standalone config beyond script naming. Narrower and clearer than `concurrently` when every task is already an npm script, but no interactive control/TUI. Current releases require a modern Node version; see its [README](https://github.com/bcomnes/npm-run-all2#installation). | An active maintenance fork, currently [9.0.3](https://github.com/bcomnes/npm-run-all2/releases/tag/v9.0.3). It is absent from this repo's locked Nixpkgs package set, so install it locally and lock it with pnpm rather than inventing a global Nix package. |
| **pnpm `run` / recursive** | Zero-extra-dependency choice for this repo's sole Node package, and especially for multi-package pnpm workspaces. | `pnpm run "/^watch:.*/"` can run matching scripts concurrently; `--sequential` serializes them. Recursive runs default to bail, `--no-bail` finishes all but still returns non-zero, `--parallel` ignores topology/concurrency limits and streams prefixed output, and `--aggregate-output` buffers each task. See the official [`run` options](https://pnpm.io/cli/run) and [recursive semantics](https://pnpm.io/cli/recursive). pnpm does not document the rich per-process signal/shutdown policy of Process Compose or `npm-run-all2`; treat it as a workspace task runner, not a daemon supervisor. | Already installed (`pnpm_11`) and cross-platform through Node. Configuration is just `package.json` plus `pnpm-workspace.yaml` when a workspace exists. Lowest added footprint for Node scripts. | Actively maintained and pinned by this repo's Nix flake; package dependencies are further pinned by each project's pnpm lockfile. Prefer it before adding another Node runner when its script/workspace semantics suffice. |

## Decision rules

- **This repository's checks/builds:** use `just`; extend the existing `[parallel]` recipe graph. Do not add `concurrently`.
- **One Node package, ordinary named scripts:** use pnpm's built-in multi-script support if its regex/ordering is sufficient; use project-local `npm-run-all2` for globbed script groups and explicit fail-fast descendant cleanup.
- **One Node package, arbitrary commands or nuanced completion policy:** use project-local `concurrently`. It remains preferable when prefixed interleaved logs, stdin routing, cross-platform quoting/shell handling, restart attempts, or “first/last/all” success and kill-on-success/failure rules are the actual requirement.
- **A developer wants one-screen interactive control of short-lived watchers:** try `mprocs`/dekit ephemerally first.
- **A recurring multi-service stack needs health checks, dependencies, reliable process-group cleanup, or headless/interactive parity:** add `process-compose` to Home Manager's shared core package list and keep `process-compose.yaml` with the owning project.
- **Long-lived or detachable sessions across projects:** keep using the already-installed `zmx`; use Overmind only for a Procfile/tmux-specific workflow.

The default therefore remains **Nix-pinned `just` globally, project-local runners locally, and no global `concurrently`**.
